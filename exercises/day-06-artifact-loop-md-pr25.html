Two /loop prompts to watch a PR and main

This PR adds one file, loop.md, at the repo root. It holds two /loop prompts to paste into Claude Code: one watches the CI and review comments of a PR, the other watches the CI of main. Both are read-only, both have stop conditions, and both cap themselves at 3 runs.

What changed

The two prompts run at different paces. The timeline below is drawn to scale in minutes. Each dot is one run and the square is the last run. The first run happens as soon as the prompt is pasted, and later runs follow the interval.

PR loop · 15mmain loop · 5m
Checks
  • PR state, reviewDecision, mergeable
  • CI through gh pr checks
  • Unresolved review threads, through GraphQL
  • New general comments since the last run
  • The last 3 runs on main through gh run list
  • If the latest run failed: gh run view --log-failed | tail -n 40, then name the failing job and step
Stops when
  • The PR is merged or closed
  • All checks pass and no thread is unresolved
  • After the 3rd run
  • The latest run has finished, pass or fail
  • The repo has no workflow yet
  • After the 3rd run
Each run prints Run n/3, then state, CI and new comments. With nothing new it prints only Run n/3 · no change. Run n/3 · sha · workflow · status · url. While a run is in progress and unchanged it prints only Run n/3 · still running.

Both prompts share the same rules: read-only, no code fixes, no re-running jobs, no replying to or resolving comments. When a loop stops, it cancels its own job with CronList and then CronDelete. A shared note at the top of the file says a loop lives only in the current session, and that every run is a full model turn that uses up Pro plan quota even when nothing changed.

Why

The goal is one standard, read-only way to watch a PR and main without retyping the prompt each time. Every /loop run is a model turn, so a prompt needs an interval, stop conditions and a hard limit from the start. The 3-run cap sets an upper bound on how much quota each loop can use.

Review blocker: is a comment resolved?

The PR loop stops when no review comment is unresolved. The first version read comments through REST, and REST has no resolved flag, so the loop could not evaluate that condition. Commit 5b8c1eb switches to GraphQL, where every review thread has isResolved.

- 3. `gh pr view <PR> --comments` and `gh api repos/…/pulls/<PR>/comments` — keep only comments that are new since the last tick and not resolved.+ 3. Unresolved review threads (REST comments have no resolved flag):+    gh api graphql -f query='query{repository(owner:"thanhtruong-agilityio",name:"claude-training"){pullRequest(number:<PR>){reviewThreads(first:100){nodes{isResolved comments(first:1){nodes{author{login} body}}}}}}}'+    keep threads with `isResolved: false`.+ 4. `gh pr view <PR> --comments` — general (non-thread) comments; keep only those new since the last tick.

Three nits

  • gh pr checks exits non-zero even when a repo has no checks at all. The prompt now says to read the output, not the exit code, and to treat "no checks reported" as CI not configured, not as a failure.
  • When a stop condition is met, the loop cancels its own job (CronList, then CronDelete). Before, it only said it had stopped.
  • The prompt now starts on the /loop line itself and drops the ### Instruction heading, so it pastes as a single command.

How it was tested

The repo contains only Markdown, with no build or test suite. Testing meant running the gh commands from the prompts against the real repo, then running one short loop with /loop.

Cron and gh work inside a session. This was a short hand-written prompt, not the prompt from loop.md.

Not tested

  • Not testedCounting Run n/3 and stopping exactly at run 3. The model counts from earlier output, and nothing enforces it.
  • Not testedThe self-cancel step (CronList, then CronDelete) running from inside the prompt. Cancelling by job id was only tried by hand.
  • Not testedThe isResolved: false filter on a real thread. Neither PR that was tried has any thread.
  • Not testedThe failed-run branch of the main loop (gh run view --log-failed), because the repo has no workflow.

When merging

  • The PR description on GitHub still covers only the first commit. It does not mention the 3-run cap, the GraphQL query or the Pro plan quota note. The author chose to leave it as is.
  • The !/loop.md line in .git/info/exclude exists only in the author's local clone and is not part of this PR. Other clones need the same line to commit a root-level file.
