# Spec: Walk-in waiting queue (check-in, queue number, call display)
From: intent.md (ThanhTruong, role TBD).

## Requirements
- R1. Reception can check in a patient at the front desk; after check-in the patient appears in the waiting queue.
- R2. Each checked-in patient is given a queue number, shown to reception at check-in.
- R3. A display shows which patient is currently being called. What it shows (name, number or both) depends on concern 2.
- R4. A doctor can see the waiting queue and who is next.
- R5. Checking in the same patient twice while they are still waiting does not create a second queue entry. (Assumption: the intent is silent; a duplicate would break R2.)
- R6. Archived patients cannot be checked in. (Assumption: carries over the existing rule that archived patients never appear in lists.)
- R7. Data stays local, with no new ports and no real patient data in tests (repo security rules).

## Design
- Backend: a new queue entry record linked to a patient, holding the queue number, check-in time and a state (waiting, called). A new router next to `patients.py`, `visits.py` and `reports.py` in `clinic-app/backend/app` exposes check-in, list-waiting and call-next. The state set beyond waiting and called depends on concern 5.
- Queue number: assigned by the backend at check-in, so two reception desks cannot get the same number. Reset rule (daily or never) is an assumption: daily, in clinic time (`clock.today()`, `Asia/Ho_Chi_Minh`).
- Reception view: a check-in action that finds an existing patient (same search as the patient list) and checks them in.
- Doctor view: a list of waiting entries ordered by check-in time, with a call-next action. Who may call is concern 4.
- Call display: a read-only page that polls the waiting-room state. The target screen is concern 3, so the design stops at "a web page".
- No link to appointments in this version; walk-ins versus booked patients is concern 1. Online appointment booking is a separate intent.
