# Plan: ticket 17, run the clinic-app tests on every pull request

Status: approved. Branch `ci/17-tests-on-pull-requests`. Source: `docs/tickets/17-clinic-app-ci-tests-on-pull-requests.md`.

## Context
The only workflow, `.github/workflows/claude.yml`, runs only on `@claude` comments. No test runs on a pull request, so "CI is green" in `docs/definition-of-done.md` cannot be met. Tests already run in Docker with `make test-backend` and `make test-frontend` (`docker compose run --rm --no-deps`, no published ports). CI reuses exactly those commands (BR2).

## Workflow design
- Name `CI`, trigger `pull_request` with `branches: [main]` (BR1). Event types default (opened, synchronize, reopened), so a new push reruns it (AC6).
- Top-level `permissions: contents: read` and no `secrets.*` (BR4, AC7). Plain `pull_request` (not `pull_request_target`), so forks get no secrets either.
- One job named `tests` on `ubuntu-latest`, `timeout-minutes: 15`.
- `concurrency` group per pull request with `cancel-in-progress: true`, so superseded pushes do not queue.
- Steps:
  1. `actions/checkout@v4` (same pin as `claude.yml`).
  2. `make test-backend` with `working-directory: clinic-app`.
  3. `make test-frontend` with `working-directory: clinic-app` and `if: ${{ !cancelled() }}` so it still runs when step 2 failed (BR3, AC5). The job is red if either step fails.
- No caching (OQ2 default), no matrix, no extra jobs.

## Risks
- **Docker build on the runner.** The backend image copies `uv:latest` from `ghcr.io` (unpinned), so a new uv release can change CI without any change in the repo. Not fixed here (out of scope); mention in the PR and consider a follow-up ticket to pin it.
- **First run time.** Two image builds (`uv sync`, `npm ci`) on a cold runner. Accepted until a run is too slow (OQ2).
- **Workflow permission.** The GitHub token used for pushes may lack Workflows write, so pushing `ci.yml` may be rejected. If so: ask the user to grant it or push/merge on the web. Do not work around it.
- **Proof needs a failing run.** AC3 to AC5 need a deliberately failing test. Done only on throwaway branches/PRs that are closed afterwards; deleting them needs an explicit yes. Never on `main`.
- **Self-hosted mismatch.** A green local run does not prove the workflow works; only an Actions run does.

## Order of work
1. Create the worktree and branch from `origin/main`.
2. Write `ci.yml`. Validate syntax locally if a tool is available (for example `actionlint`); otherwise say it was not checked.
3. Commit (`ci: run clinic-app tests on pull requests`), ask before the push, push, open the PR from the PR template. The PR itself is the first run (AC1, AC2, AC6, AC7, AC8 are visible on it).
4. Prove the red paths on throwaway branches: one with a failing backend test (AC3), one with a failing frontend test (AC4), one with both (AC5). Each as a draft PR titled "do not merge". Read the Actions logs for the failing test names.
5. Ask the user before closing the throwaway PRs and deleting their branches.
6. Tick ACs in the ticket with evidence (run links), open a follow-up commit on the ticket PR.
